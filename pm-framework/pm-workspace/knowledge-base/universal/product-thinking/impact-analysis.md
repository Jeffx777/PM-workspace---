> 改动影响面分析框架：任何功能改动在执行前，必须先绘制三层影响图——直接影响、间接依赖、潜在副作用——确保没有遗漏的破坏点。

scope: universal
来源: framework generalized PM method
提炼时间: 2026-04

---

## 适用范围

任何产品改动前的影响评估，尤其是：
- 改动核心数据模型（如：SKU 状态、用户权限、计费规则）
- 改动被多处引用的基础功能（如：商品、订单、账号体系）
- 新增规则或约束（如：禁用某类操作、新增校验逻辑）
- 废弃或下线旧功能

---

## 三层影响模型

```
改动点
  ↓
Layer 1 直接影响（Direct Impact）
  直接依赖改动点的功能和页面
  示例：禁用 SKU → 商品详情页规格选择器

  ↓
Layer 2 间接依赖（Indirect Dependencies）
  依赖 Layer 1 的功能，或与改动点共享数据/状态的功能
  示例：商品详情页规格选择器 → 加购操作 → 购物车数据

  ↓
Layer 3 潜在副作用（Side Effects）
  非预期受影响但逻辑上存在关联的功能
  示例：购物车数据 → 结算守卫 → 历史订单展示 → 数据统计报表
```

**原则**：Layer 3 越宽，改动风险越高。Layer 3 未梳理 = 改动盲区 = 线上 bug 风险。

---

## 影响面分析执行步骤

### Step 1：定义改动点
明确改什么：数据字段？接口行为？前端展示规则？业务流程约束？

### Step 2：枚举 Layer 1 直接影响
问：哪些功能/页面直接读取或展示这个数据/状态？

```
检查维度：
- 展示层：哪些页面/组件会显示这个数据？
- 操作层：哪些操作依赖这个状态？（如：加购、下单、编辑）
- 接口层：哪些 API 返回/接收这个字段？
```

### Step 3：枚举 Layer 2 间接依赖
问：Layer 1 的输出，又被谁依赖？

```
检查维度：
- 数据流：Layer 1 的数据会写入哪些下游？
- 状态同步：与 Layer 1 共享状态的模块有哪些？
- 通知链：改动触发哪些事件/消息/推送？
```

### Step 4：识别 Layer 3 潜在副作用
问：有没有非直接依赖但逻辑上相关的地方会受影响？

```
高风险副作用来源：
- 统计/报表：依赖历史数据，改动后是否影响数据口径一致性？
- 缓存：有没有缓存了改动点的数据？TTL 是多少？
- 异步任务：有没有定时任务在读取改动点的状态？
- 第三方集成：有没有外部系统同步这个数据？
```

### Step 5：评估影响等级

| 影响层 | 影响等级 | 处理建议 |
|--------|---------|---------|
| 仅 Layer 1，≤3 个点 | 低 | 直接修改 + 基本回归测试 |
| Layer 1+2，≤8 个点 | 中 | 完整修改 + 分模块回归 + 联调 |
| Layer 1+2+3 均有影响 | 高 | 拆分改动 + 灰度发布 + 监控 |
| 涉及第三方/异步/缓存 | 极高 | 需要专项测试方案 + 回滚预案 |

## 输出格式（标准影响图）

```markdown
## 影响面分析：[改动名称]

**改动点**：[明确描述改了什么，数据/接口/规则]

**Layer 1 直接影响**：
- [功能A]：[具体影响描述]
- [功能B]：[具体影响描述]

**Layer 2 间接依赖**：
- [功能C]（依赖功能A）：[影响描述]
- [功能D]（共享状态）：[影响描述]

**Layer 3 潜在副作用**：
- [报表/缓存/异步任务]：[影响描述]
- 无已知副作用（需监控）

**影响等级**：低 / 中 / 高 / 极高
**处理建议**：[基于等级的建议]
**回滚方案**：[如果上线后出问题，如何回滚]
```

## 最小改动路径原则

影响面分析的目的之一是找到"改动最小化"路径：

```
问：能不能只改 Layer 1，而不改 Layer 2 的调用方？
  → 能 = 最小改动路径（向下兼容）
  → 不能 = 破坏性改动，需要版本协调或双写过渡

问：能不能通过功能开关（Feature Flag）控制影响范围？
  → 能 = 灰度发布，逐步验证
  → 不能 = 全量发布，确保测试覆盖所有 Layer
```

---

## 反模式

- ❌ 只分析 Layer 1，认为"改的地方不多"就低估风险 → 线上事故通常来自 Layer 2-3
- ❌ 影响面分析停在讨论，不产出明确的影响图文档 → 下次改同一个点时无记录，重复踩坑
- ❌ 缓存/异步任务不在影响面分析范围内 → 改完上线后缓存未刷新，用户看到旧数据
- ❌ 影响等级评估为"高"但仍全量发布 → 应先灰度验证，再全量
- ❌ 改动涉及数据迁移但未评估历史数据 → 改完后历史数据不兼容，报表口径断裂
