> 需求价值链梳理方法：任何需求的价值判断，必须从用户目标出发，逐层向下找到最小可验证的功能单元，而不是从功能出发向上构造价值理由。

scope: universal
来源: framework generalized PM method
提炼时间: 2026-04

---

## 适用范围

任何产品阶段的需求评估、优先级排序、版本规划：
- 0→1 阶段：找核心场景，避免做多余功能
- 1→N 阶段：判断扩展方向的价值密度
- 需求评审：识别"伪需求"（从功能倒推价值的需求）

---

## 核心方法：价值链自顶向下拆解

```
Level 0：用户目标（Why）
  用户最终想达到什么状态？（业务目标/生活目标）
  示例："我想让更多人买我店里的商品"

  ↓ 拆解

Level 1：用户行为（What）
  为了达成目标，用户需要做什么事？
  示例："我需要将商品分享给潜在买家" / "我需要管理商品上架状态"

  ↓ 拆解

Level 2：功能需求（How）
  系统需要提供什么功能来支撑这个行为？
  示例："商品分享链接生成" / "规格级别的可售状态管理"

  ↓ 收窄

Level 3：本期最小范围（Minimum Viable）
  在当前阶段，哪个是必须做、做了立刻验证价值的最小单元？
  示例："先做整品分享，规格级禁用排后期" vs "先做SKU 不可用，因为客户反馈比分享更迫切"
```

---

## 价值链的两个方向

**自顶向下（推荐）**：
- 从用户目标出发，逐层向下找功能
- 优点：确保功能对应真实需求，不做无效功能
- 识别信号：能清晰回答"用户为什么需要这个？"

**自底向上（警惕）**：
- 从功能/技术出发，向上构造价值理由
- 缺点：容易产生"功能合理但用户不用"的废功能
- 识别信号：价值描述用"方便用户""提升体验"等模糊词汇，无法量化

---

## 价值链验证三问

完成价值链拆解后，用三个问题验证：

```
1. 断链测试：如果不做 Level 2 的功能，Level 1 的行为能完成吗？
   → 能完成 = 该功能不是必须的（可迭代）
   → 不能完成 = 是关键路径（优先做）

2. 替代测试：Level 1 的行为，有没有其他功能已经在支持？
   → 有替代 = 当前功能是优化，不是必须
   → 无替代 = 是新能力，需要评估价值密度

3. 量化测试：Level 2 功能做完，Level 0 目标会改变多少？
   → 可量化（提升 X% 留存 / 减少 Y 步操作）= 价值实
   → 无法量化 = 重新检查 Level 0 是否定义清楚
```

---

## 常见价值链断裂模式

| 断裂类型 | 表现 | 修复方式 |
|---------|------|---------|
| 目标不清 | Level 0 写的是功能而非目标（如"用户需要一个按钮"） | 追问："用户按了这个按钮，之后想完成什么？" |
| 行为跳跃 | Level 1 行为与 Level 0 目标不直接相关 | 补充中间行为链，找断点 |
| 功能过宽 | Level 2 一个功能对应多个 Level 1 行为 | 拆分为多个功能点，分别评估价值 |
| 范围膨胀 | Level 3 最小范围等于完整功能 | 强制问："哪个子功能可以先上线验证假设？" |

## 输出格式（标准价值链卡片）

```markdown
## 需求价值链：[需求名称]

**Level 0 用户目标**：[用户最终想达到的状态，1句话]

**Level 1 关键行为**：
- [行为1]
- [行为2]（如有多个）

**Level 2 功能映射**：
- [行为1] → [功能A]、[功能B]
- [行为2] → [功能C]

**Level 3 本期最小范围**：[功能A的核心子集] + [功能C]
排除理由：[功能B] 因 [断链/替代/量化不足] 排至下期

**价值量化**：[做了之后，Level 0 目标预期变化]
```

---

## 反模式

- ❌ 把"用户反馈了这个"当作价值链起点 → 用户反馈是信号，不是目标；需要追问背后的目标
- ❌ 价值链停在 Level 2 就做优先级决策 → 未确定最小范围，容易过度投入
- ❌ 所有功能的 Level 3 都是"完整实现" → 范围控制失效，版本永远超期
- ❌ 用"提升用户体验"作为 Level 0 目标 → 无法量化，无法验证，是逃避定义的借口
