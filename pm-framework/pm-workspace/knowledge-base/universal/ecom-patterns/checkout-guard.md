> 结算前置守卫通则：结算是订单生成的最后防线，必须在前端提交前和后端处理前双重校验商品可达性，任何依赖购物车缓存状态的结算都存在数据一致性风险。

scope: universal
来源: framework generalized ecommerce pattern
提炼时间: 2026-04

---

## 适用范围

任何电商产品的结算/下单流程，尤其是：
- 从购物车发起的结算（批量商品，状态可能在加购后变更）
- 限时活动场景（高并发下商品状态快速变化）
- 分销/联盟场景（商品状态受多方控制）

---

## 双重守卫原则

```
用户点击"去结算"
  ↓
[前端守卫] 展示结算页前，从服务端重新获取所有商品的当前状态
  ↓
  发现失效商品 → 阻断进入，在购物车页提示失效商品
  全部有效 → 展示结算页
  ↓
用户确认订单，点击"提交"
  ↓
[后端守卫] 接口层再次校验所有 SKU 的可达性
  ↓
  发现失效 → 返回明确错误码 + 失效原因，前端展示提示
  全部有效 → 生成订单
```

---

## 守卫检查项（通用）

结算守卫应检查以下维度（按优先级）：

| 检查项 | 说明 | 失败处理 |
|--------|------|---------|
| SKU 可达性 | SKU 状态是否为"可售" | 阻断 + 返回具体 SKU |
| 库存充足性 | 购买数量 ≤ 可用库存 | 阻断 + 提示库存不足 |
| 商品上架状态 | 商品是否仍在售 | 阻断 + 提示已下架 |
| 资格/权限 | 用户是否满足购买条件（会员级别/地区/限购） | 阻断 + 说明限制原因 |
| 价格一致性 | 展示价格与实际价格是否一致（防止价格竞态） | 提示价格变化，重新确认 |

## 错误反馈规范

守卫失败时，必须提供可操作的错误信息：

```
❌ 不可接受：「下单失败，请重试」
✅ 应该是：「以下商品不可购买，已为您自动取消勾选：[商品名] - [规格]（规格暂不可购）」
```

错误信息三要素：
1. **哪个商品**：精确到 SKU 级别
2. **什么原因**：用用户能理解的语言（"规格暂不可购"而非"status=disabled"）
3. **下一步**：自动取消勾选 + 引导操作

---

## 并发处理建议

高并发场景（秒杀/限时活动）的额外考虑：
- 后端守卫应使用乐观锁或库存预占机制
- 前端提交按钮应在请求期间置为 loading 防止重复提交
- 守卫失败的错误信息应区分"已售罄"和"网络超时"，前者不重试，后者可重试

---

## 反模式

- ❌ 只做前端守卫，不做后端守卫 → 并发场景下，两个用户同时通过前端守卫，后端只能接受一个
- ❌ 从购物车缓存读取状态，不重新请求 → 购物车页停留5分钟后状态已变化，守卫形同虚设
- ❌ 守卫失败只返回通用错误 → 用户不知道哪个商品有问题，被迫逐个排查
- ❌ 守卫在支付回调后才检查 → 支付已扣款但无法履行，产生退款纠纷
