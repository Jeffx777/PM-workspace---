> 配额限制引导通则：当用户触达配额上限时，关键不是"告知已满"，而是让用户看到路径——升级、释放、或等待——并能立即行动。

scope: universal
来源: framework generalized interaction pattern
提炼时间: 2026-04

---

## 适用范围

任何产品中用户遇到配额上限的场景，包括但不限于：
- SaaS 套餐席位/实例数量上限
- API 调用次数/频率上限
- 存储空间上限
- 功能授权数量上限（如：可授权小程序数、可绑定设备数）
- 免费层限制触发付费墙

---

## 配额触达的三种时机与对应处理

```
时机 A：用户看到入口时（预防式）
  → 提前在入口处展示剩余配额（如："已用 4/5"）
  → 剩余1个时开始警示色提醒
  → 剩余0时禁用入口 + Tooltip 说明 + 引导操作

时机 B：用户操作时触达（即时反馈式）
  → 操作被阻断时，展示 inline 提示或 Modal
  → 明确说明：当前配额 X / 上限 Y，已满
  → 立即给出可操作出路（升级/释放/申请）

时机 C：后台配额耗尽（异步通知式）
  → Toast/站内信告知
  → 不要只通知"已满"，同时给出路径链接
```

---

## 配额提示层级设计

| 使用比例 | 提示形式 | 文案示例 |
|---------|---------|---------|
| 0% ~ 60% | 无提示（不打扰） | — |
| 61% ~ 80% | 淡色进度条显示 | "已用 3/5" |
| 81% ~ 99% | 警告色 + 文字提示 | "配额剩余 1 个，接近上限" |
| 100% | 禁用 + 阻断提示 + 出路 | "已达上限，升级套餐可解锁更多" |

---

## 出路设计（可操作才算出路）

| 配额类型 | 第一出路 | 第二出路 | 禁止出路 |
|---------|---------|---------|---------|
| 套餐席位/数量限制 | "升级套餐" → 直跳定价页 | "管理已有 X 个" → 跳转管理列表 | "联系客服" |
| API 调用频率 | "查看用量详情" → 跳转用量分析 | "升级计划" | "请稍后重试" |
| 存储空间 | "清理空间" → 跳转清理工具 | "扩充容量" → 跳付费页 | "空间不足，无法上传" |
| 免费层功能限制 | "开通 Pro 版" → 功能对比页 | "了解更多" → 功能说明 | 直接弹付费弹窗无功能说明 |

---

## 文案规范

**禁止文案**（纯告知，无出路）：
- "您的配额已满"
- "已达到最大限制"
- "此操作不可用"

**推荐文案**（告知 + 数量 + 出路）：
- "已授权 5 个小程序，已达上限（当前套餐：5个），[升级套餐] 可授权更多"
- "本月 API 调用已用 10,000 / 10,000 次，[查看用量] 或 [升级计划] 以继续使用"
- "存储空间已满（5GB / 5GB），[清理旧文件] 或 [扩充至 50GB]"

核心文案公式：
```
已用 {当前数} / {上限数} + 出路CTA（可量化）
```

---

## 升级引导的强度与时机

不要在用户每次操作时都弹付费升级，这会产生反感。引导强度应与阻断程度匹配：

| 阻断程度 | 引导强度 | 形式 |
|---------|---------|------|
| 接近上限（剩余1） | 低强度提醒 | inline 文字提示，不阻断 |
| 恰好触达上限 | 中强度引导 | 操作被阻断 + Tooltip + CTA |
| 已超出（历史超量） | 高强度引导 | Modal + 功能对比 + 升级按钮 |

---

## 释放配额路径（重要但常被忽略）

升级不是唯一出路。如果用户不想升级，应提供释放现有配额的操作：

- 授权数量满 → "管理已授权列表" → 支持撤销授权
- 存储满 → "清理工具" → 可识别可删除文件
- 席位满 → "成员管理" → 可停用闲置账号

**原则**：先给免费出路，再给付费升级路径。避免用户感觉被"逼着付钱"。

---

## 反模式

- ❌ 配额满时直接禁用功能但不提示原因 → 用户以为是系统 bug
- ❌ 只提升级，不提释放 → 对不想付费的用户是死路
- ❌ 提示弹窗无关闭按钮或关闭后反复弹 → 骚扰用户，引发反感
- ❌ 文案只说"已满"不说当前数量/上限数量 → 用户不知道差多少
- ❌ 升级CTA跳转到首页而非定价页 → 用户找不到升级入口，放弃操作
- ❌ 在80%时就弹全屏付费弹窗 → 过度打扰，时机不对
